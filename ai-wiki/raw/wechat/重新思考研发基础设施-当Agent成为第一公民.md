## 前言：从一个周报系统说起

过去几个月，作者做了一个小系统：收集团队在多个异构系统（代码托管、项目管理、数据平台、IM）中的活动数据，聚合分析后生成一份周报。架构：connector 打通异构系统 → 规范化成统一活动流 → 用一个意图（skill）驱动聚合与排版 → 生成单文件 HTML → 推送到 Pages。

系统有三类组成部分：
1. **Agent** — 读取 SKILL.md 意图描述，连接各个数据源，动态生成 Python 脚本做数据处理
2. **代码** — 大部分是 agent 每次运行时按需生成的，生命周期很短
3. **Infra** — Pages 做托管，CI 做部署，Git 做版本控制——但对作者来说几乎"不可见"

两个关键观察：
- **代码是 generated on the fly 的** — 每次运行时根据当前意图和数据动态生成、执行、丢弃，生命周期极短
- **Infra 变得"不可见"了** — Git、CI、Pages 仍然在工作，但退到了后台

## 01 一个更本质的观察

**无论是传统研发还是 agent 研发，软件系统一直都是由"意图（不确定性）驱动 + 代码（确定性）沉淀"的进化体。** 这个模式从未改变，改变的只是驱动和沉淀的速度与机制。

传统研发：用户意图 → 产品经理压缩意图 → 研发翻译成代码 → 上线运行 → 新意图涌入。人是桥梁，循环速度周/月级别。

Agent 研发：意图（SKILL.md）→ agent 理解意图并生成代码 → 代码执行 → 结果反馈 → 意图修正。桥梁从"人"变成"agent"，循环速度压缩到分钟级。

### 三个推论

**推论一：Agent 不是革命，是加速。** 它没有改变软件进化的基本结构，只是把"意图 → 代码"的循环速度提高了几个数量级。

**推论二：静态沉淀不会消失。** 不确定性被消除后，确定性的东西就应该用确定性的方式表达——用一个巨大的概率模型去逼近一个已经确定的函数，在信息论意义上是荒谬的浪费。Agent 占比呈锯齿形：意图涌入时陡升，逻辑固化时缓降。

**推论三：模式没变，但模式对基础设施的要求彻底变了。** 当循环速度从月级到分钟级，原来为慢循环设计的基础设施就会成为瓶颈。Git 假设每次变更都值得 commit；CI/CD 假设构建和部署是离散事件；Code Review 假设有人来看每一行代码。

## 02 统一框架下的三个变量

### 桥梁带宽：从人到 agent

人的角色从"桥梁"后退为"意图的表达者"和"结果的验收者"。Agent 的优势：不丢上下文、不漏步骤、不混配置。这是认知带宽上的碾压。

### 沉淀粒度：持久代码与瞬态代码的分化

- **瞬态代码** — on the fly 生成的一次性中间产物，生命周期分钟级，用完即弃
- **沉淀代码** — 经过验证、反复出现、被证明有价值后固化下来的逻辑

### 循环频率：从发布周期到运行时反馈

从离线的、批量的、有审批流的变更，变成在线的、增量的、实时反馈的演化。"发布"这个概念本身变得模糊了。

三个变量同时变化的效果是**乘法而非加法**。

## 03 把动态性推到极致

传统软件有一个根本假设：意图可枚举。Agent 在承担研发角色之外，还会承担产品经理的部分职能——在运行时直接理解用户意图并生成执行路径。Agent 占比有一个不可压缩的下界——那部分永远没法固化成代码。

## 04 从三个案例看 agent 与 infra 的摩擦

### 案例一：多角色 agent 研发系统

基于内部研发 CLI 搭建多角色 agent 系统（discovery/delivery/examiner），覆盖从需求理解到发布上线的完整研发链路。

痛点：
- **运行环境全靠手工搭建** — 一台云服务器上同时维护多个模型入口、多套 CLI 工具、多个 agent profile、多套凭证和代理配置。需要的是 **harness**——根据角色、任务、权限范围自动组装的完整工作环境
- **研发规范没有机器可读的稳定承载** — 标准散在人的经验、历史任务、平台页面、仓库文档里
- **接口带有偏"人用"的痕迹** — MR 全局 id 和项目 iid 缺少强类型化区分，agent 经常传错
- **验证的难度梯度极大** — CLI 验证简单，app 验证困难，web 验证超级困难
- **Code Review 缺上下文** — reviewer 不知道需求是什么、为什么这么改
- **没有可重复的实验场** — 很多验证只能拿真实仓库、真实 MR 来跑

### 案例二：配置推送——agent 的自主程度取决于什么

核心对话：同事不敢让 agent 推送配置。问：如果做了严格资源归属治理和权限管控，并且提供了强 dry-run 能力？回答：如果是这样，就比较放心了。

**阻碍 agent 自主操作的瓶颈不在 agent 侧，在 infra 侧。** Agent 能不能自主操作，不取决于 agent 有多聪明，而取决于 infra 提供了多强的安全护栏。

### 案例三：身份与鉴权的碎片化

结构性原因：**角色分工曾经屏蔽了身份碎片化的复杂度。** Agent 打破了角色边界——一个 delivery agent 要 git clone（SSH）、研发 CLI 提 MR（统一鉴权）、操作中间件配置（中间件身份）、查监控（监控平台身份）。身份体系数量从"每人 2-3 套"膨胀到"每 agent 5-8 套"，频率还翻倍。

### 三个案例的共性

根源是同一个：**这些 infra 都是为人设计的。** 设计假设是：操作者有常识、有责任心、操作频率低、能从口口相传的隐性知识中填补概念的裂缝。Agent 不符合这些假设中的任何一条。

## 05 设计原则：从 People-Oriented 到 Agent-Oriented

**Agent 的自主程度是 infra 安全能力的函数。** 给 infra 补能力，而非给 agent 加限制。

四层设计原则：

### 可理解（Comprehensible）

系统的概念体系必须自洽、完整、不依赖口口相传的隐性知识。**复杂度不是问题，不一致才是。** 运行环境也要自描述——用 manifest / devcontainer 声明依赖、输入、输出、允许工具。

### 可操作（Operable）

- 可试探（dry-run / preview、幂等重试）
- 操作原子可组合（输入输出类型化）
- 隔离执行（每个任务一个 sandbox）
- 凭证不进 sandbox（通过 vault / egress proxy 注入能力）
- 渐进信任（低风险自主执行，高风险人来审批）
- 回滚能力把不可逆操作变成可逆操作

### 可感知（Observable）

**沉默和含糊是 agent 的敌人。** 状态必须 API 可查、结构化、实时。每次响应都要提供足够的语义信息让 agent 决定下一步。

### 可追溯（Traceable）

状态可恢复（snapshot / checkpoint）、过程可回放。**Agent 的失败模式是 infra 设计缺陷的放大器**——agent 反复重试某个 API 说明反馈语义不足，调用顺序混乱说明前置条件没有显式化。

四层递进关系：先理解 → 再操作 → 感知反馈 → 全程可追溯。

## 06 行业趋势与我们可以做什么

### 行业在做什么

- **并行 agent 需要并行 infra** — Superset 团队 3 人同时跑 12 个 coding agent，每天 600 个 preview deployment
- **Human DX 和 Agent DX 是正交的** — Human DX 优化可发现性，Agent DX 优化可预测性。Google Workspace CLI (gws) 从第一天就按 agent-first 设计
- **Credential Brokering 趋同** — agent 发出请求时携带占位符而非真实凭证，broker 认证后替换

### 我们可以做什么

1. **Harness 平台化** — 把 agent 运行环境变成平台的内建能力，核心约束是即时供给
2. **统一身份体系** — Agent-native 的身份，在所有 infra 上通用，远期方向是 credential brokering
3. **Dry-run 基础设施** — 统一的"变更预览"能力，输出标准化：diff + 影响范围 + 影响规模 + 风险等级 + 是否可回滚
4. **验证体系的演进** — 验证基础设施的投资优先级应该高于生成能力
5. **Agent 行为驱动的 Infra 质量度量** — 通过 agent 的行为模式来度量 infra 的 agent 友好程度

**今天的 Git、CI/CD、Code Review 系统不会消失，但它们的管辖范围会收缩到"持久化代码"的领域。** 方向已经清晰：给 infra 补能力。Infra 的能力边界，就是 agent 的自主边界。
