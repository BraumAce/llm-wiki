# AI Evals的一些实践：如何从 0 到 1 构建 agent 的评测系统？

作者：SnowThink

原文：https://mp.weixin.qq.com/s/om9KGhhMLpA5iz0XsxA3sQ

---

我搓了一个 AIGC Agent，帮自己生成公众号配图。

这玩意儿很好用，输入文章正文，它就能吐出几张风格匹配的配图。

但用了几次我就发现，我面临一个巨大的痛点：
每次的效果像抽卡，
我根本无法保证哪次生成的图更好。只能不停修改prompt，但是经常A场景变好了，B场景又不行了。

这种「薛定谔的好看」，导致我的工具迭代了三个月，水平还在原地踏步。

这是绝大多数 agent 的状态：靠感觉做决策。

我找了好久，全网也没找到做 agent 评测的小白教程，于是我自己亲身实践了一遍。这篇文章把我从 0 到 1 搭这套系统的过程拆开讲，全文免费公开，看完就能立刻上手。

Why：为什么 AI 产品必须有评测系统？

传统软件的好坏是确定性的。代码不能跑就是 bug，按钮错位就是错位，用户能不能下单是 yes/no 的问题。

AI 产品不一样。

第一，它的输出本质是概率分布——同一个输入跑两次结果可能不同；改一个 prompt 词，整体效果可能涨也可能跌；换一个模型版本，老 case 可能变好也可能变差。

第二，用户进入产品的操作其实是一个无限集，你永远不知道用户会有什么天马行空的问题。

没有经过评测的agent，是不能在生产环境中使用的。

评测系统就是把「模糊的好不好」翻译成「可决策的数字」。
它是产品经理的核心能力
。因为只有 PM 知道：业务目标是什么、什么算「做对了」、什么样的错误能容忍、什么样的错误必须修。

太长不看的agent评测6步法：

Step 1 ·业务目标 → 评测维度

Step 2 · 打造黄金数据集

Step 3 · 人评 + 机评

Step 4 · 校准AI评分系统

Step 5 · 从黄金集到生产评测集

Step 6 · Bad Case → 反推策略

以下是带有我实践例子的步骤拆解，最后还有懒人一键copy同款评测系统的prompt：

——— ◆ ———

Step 1 · 拆维度

业务目标 → 评测维度

首先要确定业务的北极星指标，但是目标本身没法直接打分，必须拆成可量化的维度。

例如，我的配图工具，业务目标是「图能让作者直接用、不需要再 PS」。这个目标拆成 4 个维度：

主题相关性
→ 图能否准确表达文章核心主题

风格一致性
→ 是否符合我给的prompt

视觉质量
→ 构图、配色、清晰度是否达标

安全合规
→ 无版权图标、无敏感符号、无 AI 瑕疵

拆维度的核心逻辑：
每个维度必须能被独立打分。
「图好不好看」不是维度，太空。「配色是否符合极简冷色调」才是维度。

目标直接决定了维度。例如，如果工具的目标是「提升用户停留时间」，那「图够不够吸引人」就成了核心维度——
业务目标决定评测维度，这是评测系统的第一性原理。

——— ◆ ———

Step 2 · 黄金集

打造黄金数据集

这里有一个很容易犯的错误，千万别想着「我得有几百个 case 才能开始」。

黄金数据集是用来校准评分器的，10 个高频场景就够。

我选 case 的原则：从过去 20 篇真实文章里挑，每个 case 必须满足三件事——是公众号常见主题、我自己亲手做过配图知道「什么算对」、包含至少 1 个有挑战的反例。

每个 case 只需要 2 个字段，文章+需求：

Case 示例

输入
→ 一篇讲「AI 时代产品经理能力变化」的文章全文复制粘贴进去

风格期望
→ 抽象人物剪影 + 热门模型logo，避免具象电脑/手机

这10个case一定要是非常仔细地筛选出来的高频典型query，因为这是所有事情的地基。

——— ◆ ———

Step 3 · 评测方案

人评 + 机评

人评太贵太慢，主力得靠 LLM-as-Judge。但模型评分有个绕不开的问题：
它评得准不准，你怎么知道？这个时候要先人工给这10个黄金case集打分。那如何打分呢？

主流的打分方式有三种：

1
GSB：两版对比首选

给两个输出，让评分者选 Good / Same / Bad。适合「新版 vs 旧版」「模型 A vs 模型 B」的二选一对比。判断成本低、信号清晰，但只能告诉你「哪个更好」，不能告诉你「好在哪、好多少」。

2
MOS：纯主观打分

让评分者按 1-5 分打整体感受，再取均值。起源于语音质量评测，现在大量用在 AIGC 主观体验评估。简单直观，但粒度太粗——你只知道「平均 3.5 分」，不知道为什么。

3
Likert：诊断性最强

把评分拆成多个维度，每个维度独立打 1-5 分。诊断性强，能精确定位是「主题不对」还是「风格不对」。设计成本高，每个维度的锚点都要写清楚。

怎么选

要快速判断哪版好 →
GSB

要给一个综合体验分 →
MOS

要找问题、要迭代产品 →
Likert

我自己用的是 Likert，按照第一部分写的主题相关性、风格一致性、
视觉质量、
安全合规这几个维度自己手动按照1-5分打分。

人工打完分之后，再让另外一个LLM当评测员给这10张图片按照同样的维度打分。在给评测员写prompt的时候，除了告诉他项目背景和打分标准，
还有一个非常重要的小技巧，也是评分 Agent Prompt 的核心设计原则：

一定要通过system prompt让打分模型暴露思考过程
。

我的 Prompt 要求模型先用 100 字客观描述图片内容，再对照风格期望按 4 个维度独立打分，每个维度必须给出打分理由并引用图片中的具体元素，最后给加权总分。

为什么要保留过程？如果最后LLM给的评测结果只有分数没有思考过程，人评和机评对不齐你也不知道哪里出了问题。

——— ◆ ———

Step 4 · 校准

校准AI评分系统

现在你有一张评测的分数表格，分别是人类的打分和LLM的打分，接下来如何校准LLM的打分呢？
我用了三个简单指标：

各个维度的分差（看单点）
→ 每个维度上人评和模型评的分数差多少。> 1 算不对齐

排序倒置率
（看整体）
→ 按均分排序，人评和模型评倒置了多少对。> 20% 算不对齐

极端 case 一致率
（看极端）
→ 人评打 5 分和 1 分的 case，模型是否也判到对应区间

我做的第一件事是把人评和模型评差距最大的 3 个 case 拉出来，逐个看模型的思维链。发现的问题：模型对「我的风格」理解模糊。它理解「极简」= 元素少，但我的「极简」是颜色不超过3个 + 有明确的视觉重点+ 有苹果的那种高级感排版，是组合判定。

总结一下我发现人评和机评不能对齐的原因，基本就是下面三种：

1
评分 Prompt 模糊

模型不知道你的标准。解法：在 prompt 里加 reference  + 明确反例。

2
评测标准本身有歧义

你自己都说不清的东西，模型当然学不会。解法：把标准拆得更原子化，更客观详细。

3
模型能力盲区

比如让一个多模态能力很差的模型去评审美，那基本凉凉，需要换一个能力更强的模型。

我改了 prompt 之后，风格一致性的均分差从 0.8 降到 0.3。
评测系统第一次有了「可信度」。

没校准过的评测系统，评一万个case也没用。

——— ◆ ———

Step 5 · 扩集

从黄金集到生产评测集

黄金集 10 个，作用是校准评分器。
生产评测集要扩到 100-500 个，作用是跑真实场景的覆盖率。

生产评测集的搭法：

1 数据来源

用户实际跑这工具输入的真实query，按主题类型提取数据。如果实在没有，构造也行。

2 清洗去重

去掉重复主题、去掉异常输入（空文章、超长文章、纯图片正文）

3 AI打标

不要全部人工打标。5% 抽样人评作为校准，剩下 95% 用LLM跑。

4 抽样组合

根据每一类query的使用频率构建评测集，一般300-500条即可。

经过上面三步，你就能得到一个非常干净、标签清晰、可以喂给agent进行打分的数据评测集了。

这里有一个我踩过的坑：只评结果不评过程，切记：

对于复杂任务的agent，结果和过程要同时评。

图最终好不好是结果。但生成这张图的过程——用了几次重试、调了什么工具、中间的具体节点——也是质量信号。一张图不好，是工具调用失败，还是loop重试次数太少，还是reviewer的标准不对？
只看结果不看过程，无法定位具体原因也就无法优化。

因此，对于链路比较长的agent最好让每一个session都单独跑评测，方便定位问题。

——— ◆ ———

Step 6 · 反推

Bad Case → 反推策略

跑完生产评测集，除了看「最后分数」，更需要
「bad case 集中在哪一类输入」
。这里有个很重要的insight：

不要聚焦于单点的case，应该把评分较低的case总结分类，从中抽象出当前最有可能影响业务核心目标的问题并拆解原因。

举个例子，我跑出来发现：概念类文章（讲哲学、讲思维方式的）配图普遍偏低分。

它告诉我：生成 prompt 在抽象主题上的隐喻能力不够。我做了两件事：在生成 prompt 里加了「抽象概念 → 视觉隐喻」的 few-shot 示例；对抽象主题的文章，自动切换到更强的图生成模型。

评测系统不是质检，它能清晰告诉你「下一步该改什么」。

这就结束了吗？并没有，评测系统一定需要动态变化。

我的黄金集每月更新一次，新增三种来源：发现的 bad case、新主题、新需求。每次接了新的更强的模型，也会跑一遍之前积累的问题，很多corner case其实可以被模型迭代所cover。

我下一步的计划是让agent自动根据评测结果，自己优化自己，真正实现自进化，human off the loop。

——— ◆ ———

Epilogue

写在最后

AI 产品时代，code is cheap，
但定义「什么是一个好的agent」这件事，需要对用户、业务、模型边界有深入理解，这种能力依旧稀缺。

因此
我认为AI产品经理的本质就是沟通者，将业务痛点翻译成能被模型理解的结构化表达，从而定义一个AI产品的最终形态。

而评测系统就是这种定义能力的载体。

如果你想给自己的 agent 搭一套评测系统，可以把下面这段话复制给你的 Claude Code：

「我想为我的 agent 搭一套评测系统。

我的产品基本情况：

- 产品类型：[文本生成 / 图像生成 / 对话 / 操作类 Agent / ...]

- 核心场景：[具体描述用户怎么用]

- 业务目标：[降低成本 / 提升体验 / 提升转化 / ...]

- 当前痛点：[换 prompt 分不清好坏 / bad case 找不到规律 / ...]

请帮我：

1. 把业务目标拆成 3-5 个可独立打分的评测维度

2. 设计 10 个高频场景的黄金 case 模板（含期望特征、评分锚点）

3. 写一个 LLM-as-Judge 的 system prompt（要求暴露思考过程）

4. 给我一份人机对齐的检查清单（怎么算对齐、不对齐怎么定位）」

最后有几个小建议：

1
先解决一个具体场景

别追求一次到位。先把这一个场景的评测系统搭起来，跑通了再扩。

2
从第一天就暴露打分的思考过程

没有思考过程的分数，是黑箱。你看不到为什么对、为什么错，迭代就无从下手。

3
校准比扩集重要十倍

一个没校准过的评分器跑 1w个 case，得到的结果没有任何参考价值。先把 10 个黄金 case 上的对齐做扎实。

4
评测集和agent都要自进化

使用AI不断将新的需求和badcase添加到评测集中，实现agent自进化。
