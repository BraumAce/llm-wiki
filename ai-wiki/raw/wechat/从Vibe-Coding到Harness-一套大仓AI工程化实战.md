# 从 Vibe Coding 到 Harness：一套大仓 AI 工程化实战

## 原文要点摘取

腾讯 TAB 是一个由 30+ 微服务、10+ 前端微应用和多平台 SDK 组成的大仓 A/B 实验平台。文章认为，跨仓需求的难点不是让模型“多写代码”，而是把 TAPD、设计文档、子仓库、沙箱、MR 与交付回写这些协作系统组织成可审计链路。一个很小的 PRD 也可能同时涉及 3 个子仓、5 个协议字段、8 个服务方法、12 个单测与接口测试。

落地从 SPEC-First 开始：先用完整的全链路技术设计明确 PRD 质量、需求分析、自动实现、集成验证四个子目标，并划分 Agent 可完成与必须人工参与的边界。作者把 Harness 拆为 Rule、Skill、Sub Agent、Workflow、Scripts、MCP 六层资产，其中可判定的约束优先下沉为 lint 或脚本，例如数据访问限制、错误码、覆盖率和事务规范；Skill 只在相应任务到来时加载，用来管理 Agent 注意力。

流程被拆成 13 个阶段，分别对应过去真实踩过的状态与验证问题。团队最终留下需求、方案、开发、代码审查 4 个角色加总控 Agent；下游角色不能改写上游产物。集成测试被前置为代码审查前的硬门禁后，开发阶段平均打回次数从 1.8 次降到 0.4 次。

文章还把交付闭环交给有语义的 MCP：TAPD、Knot、iWiki、工蜂与企微操作被收敛为明确入参、审计留痕且读多写少的接口；写操作只在初始化和交付收尾触发，并要求幂等、可软降级。作者的收束是：Harness 的四块拼图为约束与流程、反馈、知识库、进化；50+ 真实需求下，端到端耗时约 30–75 分钟、人工按按钮 2–3 次、集成测试一次通过率约 70%。
