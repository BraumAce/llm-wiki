# 从 Coder 到 Designer ：电商团队数据研发的 Harness Engineering 实践

## 项目背景

文章将 AI Data 的目标概括为“数据研发效率提升”和“数据价值交付”。其调研认为，已有单点提效 Agent、NL2SQL、ChatBI 虽能在垂直领域取得效果，但缺少可横向推广的标准接口；同时，不同团队的语义组织方案不统一，导致数据资产难以沉淀。作者把根因归为数研知识碎片化、流程非标准化，并以知识工程解决“AI 凭什么能做对”、以 Harness Engineering 解决“AI 如何稳定运行”。

## Multi-Agent 驱动的 NL2SQL

团队复用兄弟团队约 60% 的 NL2SQL 能力，自建业务域的数据资产、预定义 SQL 模板、业务语义知识库和 AI-Infra 对接。文章强调语义层是 NL2SQL 的核心：先把自然语言映射为标准化的指标—维度语义，再由语义生成 SQL，即 NL2DSL2SQL 路线。

语义资产遵循“先治理再录入”。核心指标由数研专家建模、注册和确认；以“标准名称 + 别名映射 + 语义边界”减少 GMV/交易额、活跃商家/有效商家等同义或近义词导致的召回偏差和出码错误；上线前拦截重复资产，上线后以健康度评估和冗余清理对抗资产劣化。

工作流结合顺序协作与反馈循环：Agent 按阶段完成需求分析、SPEC、资产盘点和技术方案；下游发现 SQL 质量问题时可回滚上游重新决策，关键节点保留人工干预。

## 知识工程

知识体系分为专业术语（语义层）、方法论（Spec/Plan/Task）与协作规范。SPEC、PLAN、SQL 既是阶段输出也是下一阶段输入，文档状态机驱动 8 阶段研发流程；AGENTS.md 记录协作规范，Skills 负责核心操作，Knowledge 库沉淀经验。

质量保障分三层：流程标准化（配置与技能清单）、质量把关（技术规范与人工复核）、知识管理（经验和调优方案复用）。每个需求产出的 SPEC、PLAN、SQL、验证报告归档到 Archival Memory；新增指标进入语义资产库，踩坑进入 anti-patterns.md。通用经验沉入核心配置，业务域经验按目录存放并按需求类型渐进加载。

## Harness Engineering

作者把 Harness Design 定义为面向稳定、安全、可回溯和高质量结果的外部系统设计，核心手段是分离决策与执行、分离检索与生成、以 Gate/规范/审批施加约束、管理上下文，并持续校正长程任务的行为漂移。与确定性 CI/CD 相比，它额外面对 Agent 输出的不确定性。

生产流程由 7 个 Agent 协作，采用顺序协作与反馈循环，并规定“AI 做执行，人做决策”。稳定性措施包括：技能幻觉检测 Hook 在每次技能后核对真实系统状态；关键操作必须产出文件、数据或状态变更等可验证工件；调试、换模型或换业务类型后都要重新评测并检查日志。

空间隔离要求子 Agent 根目录为 `~/.openclaw/workspace/{project_name}/`，项目按 `{domain}_{date}_{seq}` 命名；Skill/MCP 按子 Agent 的 `workspace/skills/`、`workspace/mcp/`、全局 fallback 的顺序加载，禁止跨 workspace 加载，且只开放必要能力。配置通过每日 Git 备份、agents.md 同步和模板化恢复治理。

心跳机制分为执行监控、模式识别和自动优化：从成功率、失败原因和用户修正记录中识别薄弱环节，再提出 Prompt、知识条目、超时阈值与重试策略调整。人工修正会写回知识库和规则配置，形成“执行 → 评估 → 优化 → 再执行”的循环。

## 展望与总结

近期目标是验证 7 Agent 流程、产出 Spec 规范、完成知识库冷启动；中期推进指标冲突预警、SQL 规范、自动幻觉防控、可观测性和心跳机制，并将 NL2SQL 模板用作 ChatBI 的 few-shot 素材。文章最终主张让数研人员从写代码转向需求理解、方案选型和质量决策，而 AI 负责检索、生成、部署和验证等可自动化工作。
